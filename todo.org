* DONE wandb credentials come from the host's bind-mounted $HOME, not the image :decision:
  CLOSED: [2026-08-05 Wed]
  :PROPERTIES:
  :CREATED:  [2026-08-05 Wed]
  :END:
  Rationale: Apptainer bind-mounts the host's $HOME by default; running
  `wandb login` once on the host leaves ~/.netrc where the container's wandb
  client already looks. Avoids a key ever being baked into the image or
  passed via `--env` (which would appear in shell history and
  /proc/<pid>/environ). Breaks if a run command adds --no-home/--contain —
  documented in docs/apptainer_image.md.

* DONE Fix `%post` failing with `set: Illegal option -o pipefail` :task:
  CLOSED: [2026-08-05 Wed]
  :PROPERTIES:
  :CREATED:  [2026-08-05 Wed]
  :END:
  Rationale: `apptainer build --fakeroot environment/apptainer/oa_reactdiff.sif
  environment/apptainer/oa_reactdiff.def` reached the %post scriptlet and
  failed immediately: `/.post.script: 1: set: Illegal option -o pipefail`
  (exit status 2). "Illegal option" is dash's wording, not bash's — dash
  is Apptainer's default %post interpreter unless the section itself
  starts with a shebang line naming another one. `-o pipefail` is a
  bash-only `set` option, so it fails under dash. `environment/apptainer/oa_reactdiff.def`'s
  %runscript section already opens with `#!/bin/bash` for exactly this
  reason; %post was written with the same `set -eu -o pipefail` line but
  the shebang was left off, which this build run exposed.
  Fix (not applied by Claude — implementation files are advisory-only
  per CLAUDE.md; the maintainer needs to apply this): in
  `environment/apptainer/oa_reactdiff.def`, add `#!/bin/bash` as the
  first line of the %post section, immediately before `set -eu -o pipefail`,
  mirroring %runscript. %test only uses `set -e` (POSIX-compatible), so it
  does not need the same fix, though adding the shebang there too would be
  harmless and more consistent.
  Update (2026-08-05, retried build): the maintainer added `#!/bin/bash`,
  but indented it 4 spaces to match the rest of the %post block's style —
  same error, now on line 2 (`/.post.script: 2: set: Illegal option -o
  pipefail`), meaning it's still running under dash. Root cause refined:
  Apptainer writes each section's body to the script file verbatim,
  including leading whitespace, then executes that file — it does not
  strip indentation the way the .def file's own visual layout might
  suggest. A shebang is only recognized by the kernel/shell loader when
  `#!` are the first two *bytes* of the file; `    #!/bin/bash` (leading
  spaces) is just an ordinary comment line, so the file still runs under
  the default `/bin/sh`. Refined fix: the shebang line itself must start
  in column 1 with zero leading whitespace — `#!/bin/bash` flush left —
  even though every other line in %post stays indented for readability.
  This same bug is very likely also present in %runscript's `#!/bin/bash`
  (written with the same 4-space indent, never yet exercised because the
  build has not succeeded far enough to run it) and should be fixed at
  the same time rather than discovered on a second pass.
  Update (2026-08-05, retried build again): the maintainer corrected the
  shebang to have no leading whitespace (confirmed via `grep -n bash
  oa_reactdiff.def`: `65:#!/bin/bash`, flush left) — same error,
  unchanged, still on line 2. This falsifies the indentation theory
  above; it was not the cause. Corrected finding: Apptainer executes
  %post by running a fixed shell (`/bin/sh`) on the generated script
  file; it does not exec the file directly and does not honor a shebang
  written inside the section body at all, regardless of indentation.
  This differs from %runscript, whose content becomes a file inside the
  built container that `apptainer run` execs directly at container-run
  time, where a shebang is actually meaningful. Corrected fix: remove
  `-o pipefail` from %post; `set -eu` alone is POSIX and works under
  `/bin/sh`. The section's one pipe (`curl ... | tar -xj ...`) does not
  need `pipefail` for correctness: a `curl` failure feeds `tar`
  truncated/empty input, which `tar` itself exits nonzero on, and
  `set -e` catches that. The `#!/bin/bash` line in %post has no effect
  and should be deleted rather than left in place implying otherwise.
  %runscript's `#!/bin/bash` can stay (harmless, though also not
  load-bearing, since that section has no bash-only syntax).
  Update (2026-08-05, retried build): fix applied and confirmed —
  %post now runs under bash and reaches `micromamba create`, i.e. past
  this task's original failure. Outcome: resolved.
